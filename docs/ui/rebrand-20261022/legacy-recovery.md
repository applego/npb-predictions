# 既存一覧の公開後検査と描画量の制限

PR82は新名称・UI・共有画像を本番3a9edaeへ反映した。実公開版のセ/パ/総合カード保存と390/1400px表示は成功したが、予想マトリクスと通算の追加確認で間欠的エラーを検知し、完了判定を保留した。

## 原因と修復の範囲

予想APIは337件、通算APIは794件を200で返し、同時点のfeature-healthも4系統healthyだった。一方、予想一覧は337件×12球団、通算一覧も794件を全件SSRしていた。後続の通算HTMLは正常200かつ約1.37MBで、常時のDB障害とは認定できない。全行SSRはCPU負荷の構造要因として修正するが、1102の単独根因確定とは呼ばない。

両一覧を20件ずつ描画し、全件への検索とページ送りを残す。検索で集計上の順位は変えない。予想一覧の取得失敗と真の0件を分け、失敗時は明示する。通算のpreviewが固定本番originを読む経路を、リクエストoriginへ置換する。画像・採点・既存APIの公開項目はこの修復では変更しない。

同種の見逃しは公開検査にもあった。HTTP200のエラー境界を、サイズとstatusだけでは成功と判断し得る。公開gateへ両一覧のデータ表示markerとエラー境界拒否を追加し、release-surfaceのエラー文検査も強化した。

## 再発防止と検証

- 実ReactSSR: 337件でも20件のみ、最後の17ページへ到達、全件から検索、重複queryの正規化、preview origin、API503と空データの区別（6件成功）。全行描画へ戻す反例版で2件失敗。
- shell入口: 実ローカルHTTPのPNG/HTMLを使い、正常成功と両一覧のHTTP200エラー拒否（3件成功）。エラー応答には期待markerと十分なbytesも含めた。旧gateへ戻す反例版は失敗。
- 独立レビューで、検索時の順位再付番・重複query例外・取得失敗の正常扱いを発見し修正。関連9件を独立実行して成功、追加blocking無し。
- Cloudflare向けbuildと既存性能予算は成功。実ブラウザと公開後の復旧判断は別に確認する。

未解決の既存発見はtrackerへ引受: `npb-predictions-arr`（通算採点snapshotの無順序選択、今回未修正）、`npb-predictions-3lw.2`（公開予想APIのUser全項目返却、今回新client propsへ持ち出していない）。全履歴producerの別PR80と所有者の編集は保全する。

本番で同一SHA・主要一覧の検索/ページ送り・新カード保存をread-backするまでは、この修復を4/4完了としない。

最終ローカル: unit 291件成功。実ブラウザ4件（20行上限・次ページ・検索・末尾人物の元順位・空検索・390px横溢れ0・既存badge/カテゴリ）が成功。追加差分のUBSは型補助を分離した実行でstatus=ok、8ファイル、critical0/warning24。warningは既存fetch取消し未指定、既存テストの非null、hook内のメンバー名/ローカル変数を依存要求したもの（実依存commentators/sortKey/sortDir/queryは指定済み）で、blocking無し。以前の全機能UBS停止が解決したとは扱わない。
